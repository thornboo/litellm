# 管理界面多语言实现方案

记录日期为 2026-11-07。本文保留实施前的基线与分阶段方案，当前代码进度及验证结果见[多语言实施记录](./i18n-progress.md)。

## 目标与范围

复用项目已有的 i18next 和 react-i18next，为 Dashboard、登录页及其 Chat、Playground 等前端界面增加简体中文 `zh-CN`。保留英文原文和类型检查，后续语言沿用同一套注册、加载和回退机制。

首个完整版本覆盖应用自身维护的导航、表单、提示、弹窗、空状态、校验信息和面向用户的无障碍标签。按页面和操作流程验收，不以资源文件条目数量代替实际可用程度。

本轮方案采用以下范围约定。

| 内容 | 处理方式 |
| --- | --- |
| 前端固定文案 | 提取或复用翻译键，提供英文和简体中文 |
| 模型、供应商、部署及用户创建的名称 | 保留实际名称 |
| API 字段、枚举值、路由、搜索表达式、配置键 | 保持协议和原始值，只翻译旁边的说明 |
| 示例代码、提示词、合规测试输入 | 先区分展示说明和实际请求内容，不能因翻译改变模型输入 |
| 接口错误详情、日志、模型输出、外部新闻 | 保留原始内容，可在外层提供中文标题或说明 |
| 金额、币种、时区、费用精度、导出字段 | 保留现有业务含义，只调整适合本地化的展示 |
| Python、Rust、CLI 和服务端日志 | 暂不纳入本次前端多语言任务 |

不引入新的国际化依赖，不改 API、数据库或生成的接口类型。第一版不增加语言路由前缀、账号语言字段、浏览器自动识别或在线翻译服务。

## 当前实现与官方代码核对

另外核对了官方仓库开发主线的[语言注册文件](https://github.com/BerriAI/litellm/blob/709b27e2688d229ae39fc79a9332583de84d3c30/ui/litellm-dashboard/src/i18n/languages.ts#L10)，对应提交为 `709b27e2688d229ae39fc79a9332583de84d3c30`，其语言注册表同样为空。这里核对的是官方 `main` 源码，没有验证某个已发布的 dev 镜像，也没有把上游代码合入当前 fork。

`en.json` 当前有 13,980 个叶子条目，分为 142 个顶层分组，文件大小为 875,754 字节。其中 1,400 个条目包含插值标记，289 个键带复数后缀。这些顶层分组共用现有 `translation` 命名空间，并非 142 个独立的 i18next 命名空间。

Dashboard 的 `src` 下有 1,511 个非测试 TypeScript 源码文件，其中 925 个存在 i18n 引用信号。以上是静态盘点，不能推导出页面翻译覆盖率。没有 i18n 引用的文件可能没有界面文案，有引用的文件也可能仍有遗漏。

目前语言资源目录只有 [en.json](../ui/litellm-dashboard/src/i18n/locales/en.json)。结论是基础设施和大量英文提取工作已经具备，主要任务是补中文资源、补入口、检查遗漏并完成真实界面验收。

## 技术决策

### 资源与加载

拟新增 `ui/litellm-dashboard/src/i18n/locales/zh-CN.json`，在 `LOCALES` 中注册异步加载器。英文继续随初始资源提供，中文只在选中时加载，不把完整中文资源再静态引入主初始化文件。

以 `en.json` 为键和结构的基准，保留现有 `translation` 命名空间及顶层分组。直接复用当前键，不把英文源码替换成中文，也不为这一任务重命名全站翻译键或拆分命名空间。

迁移期间只提交已审核的中文条目，其他条目通过英文回退显示。不能把整份英文复制成中文文件后宣称已完成。完整版本达到相同的叶子键集合，技术模板、品牌和协议示例可以保持原值，并记录保留原因。

现有 `_one`、`_other` 等键继续保留。中文不需要区分的分支可以使用相同译文，运行时仍按中文规则解析。通过带 count 的实际输出验证 0、1、2 等情况，不把英语复数规则写成未来所有语言必须遵守的规范。

### 默认语言与切换

第一版保留上游的首次英文默认和英文回退，用户显式选择简体中文后按浏览器记忆。登录前即可选择，不要求先用英文完成登录。

继续使用 `litellm_language` 存储语言代码，账号菜单和登录页共用现有存储、加载与切换逻辑。无效或未注册代码回退英文。退出登录不应意外清除语言偏好，需在真实流程中验证。

`DEFAULT_LANGUAGE` 当前还参与英文显示名等逻辑，不能为了默认中文直接把它改成 `zh-CN`。如果后续决定首次访问默认中文，应单独区分初始偏好和英文基准，再调整初始化行为。

第一版保留现有切换后整页刷新的行为。登录页入口放在凭据表单之外，防止切换触发提交。页面刷新会丢失未保存的输入，因此切换入口应清楚提示刷新影响；后续若确有需求，再单独设计无刷新切换和草稿保留。

### 翻译约束

保留插值变量名、格式化器、`Trans` 组件标签、链接目标和有业务含义的数值。中文可以调整句序，但不能丢变量、改变请求内容或扩大 HTML 注入能力。

`format` 分组的 9 个条目是格式模板，例如 `{{val, usd}}` 和 `{{val, timestamp}}`，保持模板本身不变。不能用“每条都包含汉字”判断翻译是否完成。

先建立简短术语表，并在每批审核时维护。建议初始用语如下。

| 原词 | 建议中文 | 约束 |
| --- | --- | --- |
| API Key | API 密钥 | 与虚拟密钥、供应商凭据区分 |
| Virtual Key | 虚拟密钥 | 不翻译实际密钥值 |
| Credentials | 凭据 | 保留供应商专有字段名 |
| Model Group | 模型组 | 不改模型组的实际标识 |
| Deployment | 部署 | 按上下文区分部署对象和部署操作 |
| Budget | 预算 | 与已发生费用区分 |
| Spend | 费用或支出 | 按页面含义统一，不与预算混用 |
| Fallback | 回退 | 保持路由配置值不变 |
| Guardrails | 安全护栏 | 保留产品或集成专有名称 |
| Token、MCP、API、AI | 保留常用缩写 | 不机械翻译协议和计量单位 |

文案采用简洁的简体中文，操作按钮使用明确动词，同一对象在导航、表单和提示中使用一致名称。自动翻译如果被采用，只作为待审核初稿，不在浏览器运行时调用翻译服务，不发送密钥、用户数据或运行日志。

## 分批实施

### 第一步，中文接入与基础界面

增加中文资源和注册，复用账号菜单，增加登录页切换入口，补齐语言加载、回退、存储和真实中文渲染的测试。

首批范围为以下 16 个现有资源分组，共 680 个叶子条目，其中包含前述 9 个保持不变的格式模板。

`format`、`shell`、`login`、`onboarding`、`changePassword`、`home`、`shared`、`commonComponents`、`toast`、`networking`、`utils`、`themeToggle`、`ui`、`uiTheme`、`docsMenu`、`apiReference`。

验收登录、初始化、退出、导航、账号菜单、修改密码、常用提示和语言切换。此时其他业务页面允许英文回退，在进度文档中明确列为未完成。通过这一批校准审核速度，再估算后续时间。

### 第二步，核心管理流程

优先覆盖密钥创建和编辑、模型与部署管理、预算、用量、费用和日志，以及组织、团队、用户、项目等常用流程。以可执行的用户流程切分批次，不要求一次改完全部大文件。

每批同时检查资源、组件中的固定英文、校验错误、弹窗、空列表和通知。相应表单需要证明英文与中文提交的业务参数一致，权限、路由和筛选语义不变。

检查遗留的数字和日期展示，先追踪调用者再修改。纯 UI 格式与请求、导出和计费格式分别判断，避免把展示本地化传播到业务数据。

### 第三步，高级页面与完整资源

覆盖 Playground、Chat、MCP、Guardrails、Agents、提示词、技能、向量存储、策略、管理和设置等剩余模块，完成既定界面范围的全部资源审核。

对包含提示词、请求示例、供应商参数的条目逐项分类。翻译说明文本，保留作为模型输入、配置值或协议示例的内容。动态外部内容按前述边界保留原文。

中文资源最终与英文键集合对齐，保留值均有明确原因。若同一英文键被上游修改，即使键没有变化，也要重新审核对应中文。

### 第四步，遗漏与发布验收

按桌面和窄窗口检查表格、弹窗、侧栏、长说明和空状态，修复截断、宽度及无障碍名称问题。扫描源码中的剩余固定文案，并人工区分技术示例、用户内容和实际遗漏。

验证中文命令面板搜索、语言刷新恢复、英文回切、资源加载失败、金额日期和生产构建。保存真实浏览器流程的截图与复现步骤。全部约定页面通过后，才把文档状态改为完整交付。

## 验收与验证

### 功能验收

| 验收项 | 必须证明的结果 |
| --- | --- |
| 语言入口 | 登录页和账号菜单均可选择英文、简体中文，语言名称易识别 |
| 偏好恢复 | 选中文后刷新、导航和退出登录仍保留选择，切回英文同样有效 |
| 异常回退 | 无效存储值、缺少翻译键、中文加载失败时界面可用，没有裸键和永久加载 |
| 首次渲染 | 已保存中文时只读一次的标签正确，没有 hydration 错误，最终 HTML lang 正确 |
| 资源正确性 | 已验收批次的界面文案均已审核，插值、格式化器和 Trans 标签正确，复数输出可用 |
| 行为一致 | 中文和英文的登录、筛选、创建、编辑使用同一业务参数，权限和跳转一致 |
| 金额和时间 | USD 仍为 USD，小额价格不变成零，到期日期时区和日期边界不变 |
| 搜索与术语 | 中文导航可搜索，查询 DSL 不变，AI/SI 术语开关保持产品含义 |
| 视觉与可访问性 | 桌面和窄窗口关键流程无影响操作的截断，用户可感知的辅助名称已本地化 |
| 生产产物 | 按需语言资源进入构建，生产静态导出成功，现有检查阈值保持不变 |

### 测试方式

扩展现有语言测试，对真实中文资源做结构、插值变量、组件标签和实际渲染验证。迁移期只要求已声明批次完整，最终版本再要求全量键对齐。保留按语言解析的运行时测试，不能只比较 JSON 结构。

扩展 Provider 和语言选择组件测试，覆盖真实中文、缺失键、加载失败、保存偏好和刷新调用。登录页测试覆盖切换不提交凭据，以及原有登录行为。核心表单测试比较翻译前后的业务载荷，使用受控依赖，避免真实供应商费用。

针对遗留格式化修复扩展其已有测试文件，证明精度、UTC 边界和原有无效值处理。类型测试继续使用 [i18n.test-d.ts](../ui/litellm-dashboard/src/i18n/i18n.test-d.ts)，保持英文键的类型检查能力。

单元和组件测试按明确文件运行，不运行整站 Vitest 全量测试。应用实施后再按实际改动执行相关 lint、类型检查和构建，不降低检查或覆盖率门槛。

浏览器验收使用现有本地前端和代理，保留操作路径、输入、截图和结果。纯语言展示无需真实模型调用。需要写入演示数据的流程使用可识别的本地测试记录并在验证后清理，不变更已有账号权限或真实配置。

### Docker 与环境约束

继续使用现有容器完成依赖安装、开发和验证，不在宿主机安装 Node、Python 或 Rust，不修改 mise、全局 PATH、Shell 配置和 Docker/Colima 设置。

当前已有相关测试可在前端容器中执行。

```sh
docker --context colima exec litellm_local-frontend-1 npx vitest run --project unit --maxWorkers=1 src/i18n/languages.test.ts src/i18n/locales.test.ts src/i18n/formats.test.ts
docker --context colima exec litellm_local-frontend-1 npx vitest run --project component --maxWorkers=1 src/i18n/I18nProvider.test.tsx src/components/SidebarAccountMenu/LanguageField.test.tsx
```

这两条是现有基线检查，实施时还要增加实际修改文件对应的测试。不要在正在提供开发服务的前端容器中运行生产构建，因为其 `.next` 缓存会受到影响。生产构建应使用包含最新代码的临时容器，不挂载现有开发服务的缓存卷，先检查可用资源再运行。

## 风险与控制

| 风险 | 控制方式 |
| --- | --- |
| 大量条目翻完但页面仍夹杂英文 | 资源批次与真实页面状态共同验收，残留扫描只作候选清单 |
| 翻译破坏插值、富文本或请求示例 | 自动校验加实际渲染，逐项区分展示与请求内容 |
| 切换刷新丢失未保存表单 | 第一版说明刷新影响，入口避开提交动作，后续单独评估草稿保护 |
| 资源加载、缓存和初始化顺序问题 | 复用门控，验证刷新、失败回退及只读一次的标签 |
| 费用或日期含义改变 | 只改展示层，保留币种、精度和时区，扩展边界回归测试 |
| 中文资源体积影响启动 | 中文按需加载，检查生产产物和首次切换，不提前改造全站资源拆分 |
| 上游新增或修改英文键 | 英文变更逐批对照，新增键暂时回退并登记，已有键改文案也复核中文 |
| 单个中文 JSON 的多人编辑冲突 | 按分组分配内容，由单一集成者合并资源，不同时重排整份文件 |

## 方案阶段的验证基线

本轮已核对官方开发主线的语言注册文件，盘点本地基础设施及资源，并在现有前端容器运行 5 个测试文件，共 42 项通过。分别为 3 个单元测试文件的 32 项，以及 2 个组件测试文件的 10 项。

测试输出存在既有 Vitest 环境 API 的弃用提示，不影响本轮通过结果。上述结果只证明当前英文和多语言基础机制的基线，不能作为尚未实现的中文功能验收。

方案阶段仅交付 `dev-zz` 文档。实施从第一步开始，先交付可在登录页切换、可刷新恢复的简体中文基础界面，再按页面推进其余范围。
